1. El Orden de Ejecución es clave

Antes de tocar el código, debéis entender que las bases de datos tienen jerarquías. Si intentáis borrar una columna que es necesaria para otra tabla, el sistema os dará error.

  • Buscad la diferencia entre DROP, ALTER y TRUNCATE. No son lo mismo y usarlos mal puede borrar datos irreproducibles.
  • Realizad siempre un "script de limpieza" que permita borrar lo creado y empezar de cero si algo sale mal.

2. La tabla address

La tabla address es el punto más complejo del proyecto. No se trata solo de crear una tabla, sino de mover datos entre tablas sin perderlos.

  1. Cread la tabla address.
  2. Investigad la sentencia INSERT INTO ... SELECT. ¿Cómo podéis aseguraros de que no se inserten direcciones duplicadas? (Pista: cláusula DISTINCT).
  3. Antes de borrar las columnas viejas en customers o employees, debéis crear una columna id_address en ellas y "vincularlas" con la nueva tabla.
  4. ¿Cómo se actualiza una tabla basada en los datos de otra? Buscad: "MySQL UPDATE JOIN syntax".

3. En referencia a las restricciones

Las restricciones (constraints) constituyen las reglas del juego de una Base de Datos. Hablemos de algunas de ellas:

  • Restricción UNIQUE: ⚠️ Cuidado. Si intentáis poner UNIQUE en una columna que ya tiene datos repetidos, MySQL fallará. Primero debéis limpiar los datos.
  • Relaciones: Al definir las foreign keys, pensad en el negocio: Si borro a un empleado, ¿debo borrar todas sus ventas pasadas (CASCADE) o simplemente dejar el registro sin vendedor asignado (SET NULL)?
    Justificad este tipo de decisiones en vuestra entrega.

4. Lógica de Triggers (Disparadores)

Los triggers son como 👮🏽‍♂️ policías 24/7 que vigilan la tabla para la cual han sido creados.

A tomar en cuenta:

  • NEW vs OLD: Para validar un INSERT, usad NEW.nombre-de-campo. Para un UPDATE, podéis comparar OLD (lo que había) con NEW (lo que se quiere actualizar).
  • Validaciones Complejas: Para programar la lógica de validación de emails investigad el uso de Expresiones Regulares (REGEXP) en MySQL. Es la forma profesional de validar formatos de texto.
  • Detener una operación: Un trigger no se utiliza para avisar, debería detener una operación incorrecta. Buscad cómo usar SIGNAL SQLSTATE para lanzar un error personalizado que impida que un dato inválido entre en la base de datos.

6. Pruebas (Ejemplos)

En SQL, que un script se ejecute sin errores de color rojo no significa que el trabajo esté bien hecho; significa que la sintaxis es correcta. La verdadera calidad está en que los datos resultantes sean coherentes.

Antes de generar el PDF final, realizad las siguientes pruebas en vuestro entorno de AWS. Si el sistema os permite hacer algo "prohibido", significa que vuestra restricción o trigger tiene un fallo de lógica.

A. Prueba de Integridad de Datos (CHECK)

Intentad insertar un registro que rompa las reglas de negocio:

  • En la tabla invoice_lines: Intentad un realizar un INSERT con quantity = 0 o -1.
    Resultado esperado: El sistema debe dar un error y rechazar la fila.
  • En la tabla employees Intentad hacer un UPDATE donde el campo hire_date sea el año 1980 y el campo birth_date sea 1990.
    Resultado esperado: Error de restricción (o el trigger de validación debe saltar).

B. Pruebas de Seguridad (Triggers de Password)

No asumir que el trigger funciona solo porque el código para crearlo se ejecutó sin errores. Probadlo. Ejemplos:

  • Prueba fallida núm. 1: Intentad realizar un UPDATE en customers poniendo pwd = '123'. (Falla por longitud).
  • Prueba fallida núm. 2: Intentad ahora pwd = 'Abcdefgh'. (Falla por falta de símbolos o números).
  • Prueba Exitosa: Intentad pwd = 'Admin_2024'. (Debería permitirlo).

C. Pruebas de Formato (Triggers de Email)

En la tabla employees:

  • Intentad insertar un email como pepito.perez@com (sin el .es, .com, etc., o mal formado).
  • Intentad insertar pepito#perez@empresa.com.

En ambos casos, el trigger debería usar SIGNAL SQLSTATE para detener la operación y mostrar vuestro mensaje personalizado.
