[P1] Modificación de una base de datos. Restricciones y disparadores

Descripción ❋

Para el presente proyecto, usaremos la base de datos Chinook.

La Base de Datos Chinook es una Base de Datos ficticia que simula una tienda de música digital. Se creó como alternativa a la base de datos de ejemplo llamada Northwind que viene con la instalación de motor de base de datos SQL Server. La base de datos puede ser cargada en distintos motores de bases de datos entre los que se encuentran SQL Server, Oracle, SQLite, PostgreSQL, DB2 y por supuesto MySQL.

Los datos relacionados con las pistas/tracks se crearon utilizando datos reales de una biblioteca de iTunes. La información de clientes y empleados se creó manualmente utilizando nombres ficticios, direcciones que se pueden ubicar en los mapas de Google y otros datos (teléfono, fax, correo electrónico, etc.). La información de ventas se generó automáticamente utilizando datos aleatorios durante un período de cuatro años.

Es una base de datos que consta de once tablas, las cuales se encuentran referenciadas en el contenido del proyecto, en la Fase 3:

Analizaremos las tablas, crearemos las restricciones así como algunos campos e implementaremos algunos disparadores los cuales nos permitirán mejorar su funcionalidad.

Objetivos ⚑

  • Ser capaces de analizar una Base de Datos existente generando el modelo entidad‐relación en Workbench a partir de ingeniería inversa.
  • Modificar la arquitectura inicial de una Base de Datos, optimizando los diferentes tipos de restricciones.
  • Implementar disparadores para complementar las restricciones existentes y generar información histórica y tablas de auditoría.

Claves Foráneas

  • ¿Para qué se utilizan y cuáles son los beneficios de utilizar claves foráneas?
  • Cuando dos tablas se encuentran relacionadas, cualquier acción de actualización o eliminación de las filas de la tabla principal (aquella que contiene la clave primaria) debe reflejarse en consecuencia en la tabla relacionada (la que contiene la clave foránea). La restricción FOREIGN KEY ofrece varias opciones para implementar estas actualizaciones o eliminaciones. Revisar cada una de éstas opciones o cláusulas analizando qué sucedería si la restricción FOREIGN KEY se configura de una manera u otra.

La base de datos Chinook está parcialmente normalizada, pero no cumple estrictamente con todas las formas normales. La normalización busca reducir la redundancia y mejorar la integridad de los datos. Chinook cumple con algunas, pero tiene áreas que podrían mejorarse. En este producto abordaremos algunas pocas mejoras.

Por ejemplo, en la tabla Invoices, es posible que la dirección del envío a un cliente (junto con la ciudad, país y código postal) se repita en cada factura. Adicionalmente, un cliente puede tener una dirección de facturación y varias direcciones de envío. Para evitar redundancia, se pueden mover todos los campos de dirección desde las tablas Customer, Employee e Invoice a una tabla separada de direcciones (Address), teniendo cuidado de que no se repitan y referenciar las direcciones desde las tablas Customer, Employee e Invoice.

  1. Importar las tablas de la Base de Datos Chinook al servidor de Base de Datos AWS, utilizando el Schema asignado al grupo.
  2. Crear una tabla Address para reutilizar direcciones entre empleados, clientes y facturas, agregando un IdAddress (autonumérico) y AddressType (enum) con los valores Customer, Employee, Billing. Sustituir las direcciones pertinentes en las tablas por el IdAddress de la dirección de la tabla Address.
    Antes de eliminar las columnas de dirección en Customer, Employee e Invoice, lo ideal es migrar esos datos a una tabla temporal, insertando direcciones únicas, que poblarán finalmente la tabla Address, llenando el campo enum que identifica su origen. Esto es importante para no perder datos.
  3. Crear los siguiente campos en la tabla customer: VIP (enum: sí, no; default: no), birthdate (date), username (VARCHAR(12)) y pwd (VARCHAR(12)).
  4. Crear los siguientes campos: discount (decimal(5,2)) y SubTotal (decimal(10,2)) en la tabla InvoiceLine; y SameAsCustomer (enum: sí, no) en la tabla Invoice
  5. Crear una restricción de tipo CHECK al campo Quantity de la tabla invoiceline que controle que no se puedan introducir cantidades menores a 1.
  6. Crear una restricción de tipo CHECK al campo HireDate de la tabla employee que controle que el valor del campo HireDate, sea mayor al valor del campo Birthday.
  7. Crear una restricción de tipo UNIQUE a los campos ArtistName, GenreName, PlayListName y MediaTypeName. Comentar si habéis podido hacerlo, qué habéis tenido que corregir y qué consecuencia tiene haber colocado estas restricciones.
  8. Relacionar las tablas de la Base de Datos tomando en cuenta el modelo adjunto junto con los scripts para importarla. Al crear las claves foráneas, agregar las cláusulas ON UPDATE y ON DELETE pertinentes, justificando con un comentario cada decisión.

  9. La siguiente instrucción:

    UPDATE mytable
    SET mycolumn = STR_TO_DATE(
    CONCAT(
      LPAD(FLOOR(1 + RAND() * 12), 2, '0'), '-', -- Mes (01–12)
      LPAD(FLOOR(1 + RAND() * 28), 2, '0'), '-', -- Día (01–28)
      FLOOR(1940 + RAND() * (2007 - 1940)) -- Año (1940–2006)
    ),
    '%m-%d-%Y'
    );

    permite actualizar un campo fecha de una tabla con fechas aleatorias (en este caso el año de nacimiento estaría en el rango 2007-1940, y los días entre 1 y 28).
    La función LPAD, asegura que el mes y día tengan dos dígitos.

    Actualizar el campo birthdate de la tabla customer.

  10. Actualizar el campo discount de la tabla invoiceLine utilizando la función rand() de MySQL para que tome valores entre 0% y 10%. Eliminar el campo Subtotal y volverlo a crear como un campo autogenerado que muestre el precio de la línea tomando en cuenta cantidad (Quantity) y el descuento (discount) previamente actualizado.
  11. Actualizar (UPDATE ) el campo username de la tabla customer de la siguiente manera: inicial de su nombre en minúsculas + las tres primeras letras de su apellido en minusculas + id de su Representante de Ventas + un guión de subrayado + las dos primeras letras de su país en mayúsculas. (Una sola instrucción debe actualizar toda la tabla)
  12. Actualizar el campo pwd con el contenido del campo username previamente actualizado.

  13. Crear dos disparadores para que al intentar cambiar un registro de la tabla customer (BEFORE UPDATE) o se intente incluir un nuevo cliente (BEFORE INSERT), revise si el campo pwd longitud es mayor a 7 caracteres y su contenido contiene mayúsculas, minúsculas, digitos y alguno de los siguientes símbolos: -_#@. De no ser así, mostrar un mensaje de error (SQLSTATE) y no permitir la operación.

  14. Diseñar dos disparadores que prevenga que el campo email de la tabla employee tenga un formato correcto al actualizar o insertar un nuevo email.
